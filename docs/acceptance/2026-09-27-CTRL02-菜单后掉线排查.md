# CTRL‑02 菜单后掉线排查（2026-09-27）

## 现场证据

- ESP‑02 单独接 USB‑TTL 运行时，COM5 先输出 `#BOOT`、`#WIFI connecting`，随后 50 秒持续输出 `LINK|1|1|0`，本地 MQTT 状态保持 `online`。
- ESP‑02 接回 Node B 后，Broker 多次记录 `Client CTRL-02 ... disconnected: session taken over`，间隔约 5–20 秒；状态主题 `offline` 后约 20–50 毫秒再次 `online`。同一观察窗口内未收到 CTRL‑02 转发的遥测或菜单命令。
- COM3 的 Node B 日志可见 `LINK|0|0|0` 的残片及异常字节；同时，Node B 发出的 `ut.node-b.status.v1` 同序号帧又以 `#ESP` 输入回到 Node B。ESP‑02 固件没有原样回送 Node B 状态帧的路径，需检查 USART2 TX/RX 回环或并接冲突。
- 原始观察记录：`artifacts/bench/ctrl02-menu-trigger-20260927-com3.log`、`ctrl02-menu-trigger-20260927-mqtt.log` 和 `ctrl02-menu-trigger-20260927-serial.log`。COM5 对应 Node A；COM3 对应 Node B。

## 固件发现与修复

ESP8266 Arduino 框架的 loop 栈是 4096 字节。旧版 `screen_routing.cpp::updateTelemetry` 在处理 Node A 遥测的 MQTT 回调中同时创建 `TelemetryAccumulator`（本机结构大小 1960 字节）和 `ScreenSnapshot`（1936 字节）两个局部副本，合计 3896 字节，尚未计入回调和 JSON 解析栈帧。这个栈占用足以解释在接收跨节点数据后重启并反复重新连接，但现场尚未取得复位原因码，不能把它认定为唯一原因。

修复版将事务副本移出回调栈，并在构建单条轮转快照后恢复完整传感器数组。CTRL‑02 构建、CTRL‑01 构建、屏幕路由主机测试和主程序契约测试均通过。CTRL‑02 修复映像 SHA‑256：`1228E1F1D1B16BD8728452B845F097BD3CB7A96FAFADE06FBDC665279B8A163C`。

## 烧录与待实机核对

COM5 通过 ROM 启动信息确认进入下载模式，以 9600 波特率识别 ESP8266EX，MAC `8c:8c:29:a3:b9:63` 与 CTRL‑02 历史记录一致。修复版写入 317152 字节，写入摘要校验成功；随后独立 `verify-flash` 返回 `Verification successful (digest matched)`。

恢复 GPIO0 后，ESP‑02 单独运行 45 秒，`LINK|1|1|1`、Broker `online` 持续稳定。重新接回 Node B 后，于 17:39:18–17:40:23 同步观察 COM3 与 Broker：CTRL‑02 状态 `online` 1 次、`offline` 0 次；收到 31 帧 CTRL‑02 遥测、9 条菜单命令；COM3 明确见 8 条 `accepted` 回执。窗口末尾的第 9 条菜单命令回执不在已留存窗口内，不计为确认。该窗口内未见 `#BOOT`、`#WIFI reconnect`、`MQTT|DOWN` 或 Node B 自身状态帧经 `#ESP` 回环，Broker 也未再记录 CTRL‑02 session takeover。

修复版和重新接线后的短时复测通过；两项变化同时发生，现有证据不能单独量化栈修复与接线修复各自的贡献。建议保留接线现状并做更长时段的稳定性观察。
