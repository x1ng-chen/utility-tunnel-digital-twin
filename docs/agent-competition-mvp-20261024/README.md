# 管廊运维Agent：三个参赛演示场景与验收基线

版本V0.1，2026-10-24。性质：本轮开发工作基线，非赛事官方评分、获奖预测或已通过验收。用户当前要求先规划；本轮仅整理场景、实施顺序与记录模板，不修改运行代码、不调用付费模型、不购买云资源、不发布作品。

## 1. 作品主线与当前事实

目标：让Agent围绕一个明确运维任务，从有时间和质量标记的数据中获取证据，比较候选原因，定位相关设备，形成可人工确认的工单，并在后续查询时核对恢复证据。

本轮只围绕三个场景开发：S1五站巡检、S2多源证据排障、S3工单与恢复复核。小智和公网是这些场景的入口与交付方式，后接同一业务服务。现有31路、四主控、两风机、两INA226及700×700×300 mm布局继续沿用。

| 已检查的依据 | 可以复用 | 尚不能声称 |
| --- | --- | --- |
| `backend/operations/ai_assistant.py` | 7个白名单工具、模型工具循环、质量/时间、草案前置检查 | 完整多站排障、预测事故或已确定根因 |
| `frontend/src/components/AiAssistant.vue` | 工具证据展示、人工确认、创建工单与同键重试 | Agent已经触发三维选择、高亮和相机定位 |

## 2. 一致的数据与身份约定

- 区分物理标签、平台assetCode、站点和主控，不按数组位置重新编号。P3/P5同属CTRL-03，不能因为站点相近而替换所属控制器。
- 读取V16候选映射，使用时与真实台账/硬件绑定/GLB逐项核对。尤其MQ2-01→SMOKE-01、MQ4-01→GAS-CH4-01、CO-01→GAS-CO-01，不改成看似整齐的新编码。
- 五站直接气体/火焰成员20路，温湿度/液位/氧气11路为邻近上下文；合计31路。INA226两路另计。不能只查20路却声称完成全系统巡检。
- 每个输入标记`REAL_TELEMETRY`、`HISTORICAL_REPLAY`或`SIMULATED_TEST`，带采样/入库/查询时间与质量。模拟与回放不改成“现场实时”。
- 具体metric_key、量纲、规则阈值、风机转速/电流绑定在隔离测试环境盘点后填入；本规划不发明数据库中不存在的指标。配置不完整时应显示缺失，不伪造正常值。
- 气体未经标定保留ADC/电压，MQ-2使用DO报警；AO-02按用户指定裸探头直连，精度未验收。不能自动产生可信ppm、精确氧浓度或人员可进入结论。

## 3. S1：五站巡检与可信状态总览

提示词：“检查P1到P5，分别告诉我哪些检测正常、哪些触发告警、哪些数据已经过期，列出优先检查项并定位到设备。”

准备条件：隔离数据库中31路候选身份已核对；设置统一测试时钟T0，输入数据带来源/质量；明确启用规则和在线判定配置。默认不加危险工况。

目标步骤：

1. 获取五站及11路上下文的批量快照与覆盖清单。
2. 区分阈值告警、通信过期、坏质量、未接入和正常采样；“无活动告警”不能替代质量检查。
3. 显示31路覆盖数、缺失数及各站明细，以确定性规则整理优先级并说明依据；缺少风险配置时不声称精确风险排序。
4. 展示相应证据编号、采样时间和可操作的设备定位卡片；卡片触发现有三维组件选择/高亮/相机定位，不能任由模型指定任意mesh字符串。

必须满足：31路每路唯一计入或明确缺失，P1～P5不串站；坏质量/未来时间/过期不能被归入正常；同名同类传感器不混淆；点击定位落到绑定目标，缺失绑定时明确拒绝定位。

用例：INS-01全部新鲜；INS-02右上节点超出在线宽限；INS-03单传感器坏质量或未来时间；INS-04一条台账/模型绑定缺失。详见[cases.json](cases.json)。

## 4. S2：P5告警与排风状态的多源证据排障

提示词：“核查P5这条告警，结合最近10分钟邻站数据、两台风机的供电/转速/电流和相关手册，列出可能原因、证据及还需要人工检查的项目，定位相关设备。”

准备条件：所有气体变化与故障均在隔离测试数据中注入；不使用真实危险气体、明火或堵转试验。风机“已请求开机、命令回执、继电器状态、转速、电流”分别取证；没有采集或回执时按缺失处理，不用命令值冒充实际状态。

目标步骤：

1. 确认告警关联真实assetCode，核对时间和数据质量。
2. 比较P5与可用邻站同类指标；保持单位、传感器标定和窗口一致。不同探头原始ADC不可直接作等浓度比较；跨探头只展示各自变化及限制。
3. 获取风机状态证据，按版本化的规则/案例生成候选原因。例如“供电可能中断”“测速链路可能异常”“负载异常需要检查”，不把相关性说成唯一根因。
4. 从有来源、版本和适用范围的知识条目取证，组织“已知事实—候选原因—反证/缺口—建议核查”。不输出虚构置信度。
5. 定位P5具体传感器及相关风机，提出工单建议；不直接执行设备控制。

必须满足：至少引用告警、测量/趋势及执行器观测这些实际可用证据；关键证据缺失就降低结论强度。数据不支持故障归因时，返回“无法判定”，并给出下一项可核查信息。引用必须能在证据面板/知识条目中找到。

四个模拟变体：DIA-01风机请求启动且供电观测异常；DIA-02电流存在但测速缺失；DIA-03仅P5单探头异常而其他证据正常；DIA-04邻站或执行器数据过期。各变体的允许结论和禁止结论见用例表。

## 5. S3：工单协作与恢复证据复核

提示词：“针对刚才核查的设备，先检查未完成工单，再生成处置草案。我确认后创建，并显示真实编号；后续根据新采样和处置记录复核恢复情况。”

准备条件：专用测试用户与演示工单；固定操作对象，避免“刚才那台”指代不清。每次进入新请求时重新读取关键证据，不把上一轮自然语言当现场事实。

目标步骤：查询资产/数据、已有工单→有权限时生成草案→显示关联资产、建议和证据→人工审阅确认→既有工单API写入并返回真实编号→用户再次请求复核时读取新采样、告警、风机观测和处置记录。

必须满足：确认前和取消后新增工单均为0；只读用户无法生成可提交草案或越权创建；同一确认请求响应丢失时复用原幂等键，至多产生1条工单。发现已有同类工单时优先展示并避免无提示重复创建；不声称实现了目前尚无的跨会话语义去重。恢复通信、测量恢复、设备恢复、工单完成分别核对，均无权自动推导为“已安全处置/自动关闭”。

四个用例：ORD-01确认创建；ORD-02已有工单；ORD-03查看者越权与运维员取消两条分支；ORD-04响应丢失重试并恢复复核。

## 6. 优先开发清单与依赖

| 顺序 | 工作项 | 交付/完成条件 |
| --- | --- | --- |
| 1 | 台账/指标/模型映射盘点，隔离数据集 | 31路对照表，风机/INA/转速/回执可用性表，固定T0与来源标签，未接入项显式列出 |
| 2 | 批量站点快照与覆盖检查 | 工具可一次取得限定范围及31路覆盖，字段白名单、权限、条数/时窗上限和缺失状态明确 |
| 3 | 三维定位交互 | Agent返回受校验assetCode，前端卡片解析已核对映射；五站和同站多个报警均正确，无绑定拒绝 |
| 4 | 多源排障和有来源知识 | 时间对齐、原始量限制、风机观测区分、候选原因/反证/缺口；资料版本与出处可查 |
| 5 | 工单与恢复复核 | 原创建接口/幂等/人工确认复用，先查已有工单，复核不代替人工结单 |
| 6 | 真实模型评测、对照及演示脚本 | 实际回复、工具轨迹、事实核对和失败记录；不以mock替代 |
| 7 | 小智、评审权限与公网交付 | 接同一业务Agent；受限评审账号、可用HTTPS、来源/离线状态、匿名材料 |

现有单请求最多6次工具调用、4轮模型调用。批量快照优先解决覆盖问题，初版保留上限；S2可能分成“核查”和“生成草案”两个明确请求，S3新请求重查必要证据。达到上限时返回未覆盖内容，不静默省略。是否调整预算以真实用例耗时/费用决定，不先无限增加调用数。

现有离线手册仍写“双节点/ESP8266”，需按四STM32→RS485→S3→MQTT→平台修订，并保留历史版适用范围。新资料不能直接冒充已批准现场规程。

## 7. 验收、对照与记录

所有12个用例初始均为NOT_RUN。现有30题作为数据/权限回归保留，另测本表12个复合场景，不将两者混成一次已完成测试。

团队开发目标（不是官方门槛）：三个主流程均可完成；12个固定用例逐项通过或修复重测后通过；严重事实捏造、越权写入、串设备、数据过期显示正常、来源伪装、确认前写工单均不得遗留。对存在能力缺失的用例标BLOCKED，不能以“不适用”美化完成率。

对照条件：

- M：人工在同一平台完成任务，可以查同一版知识资料。
- L：相同模型、无自动工具调用；人工提供等价快照/资料，提供过程所花时间计入。不得在模型上下文中泄露预设故障原因。
- A：本项目Agent自动调用受限工具；获得的信息范围与M/L相同。

初轮12个固定用例在M/L/A各执行1次，总计36次任务，其中24次需要真实模型调用。若先完成A组，再补M/L，只有相同代码、数据和配置下的A组结果才能沿用。重要或不稳定用例再重复，报告实际次数。人工与模型材料准备时间分别记录；缓存状态/网络条件/操作者熟练度及执行顺序要记录，不能预设效率提高比例。小样本不外推生产可靠性。

记录模板见[evaluation-record-template.csv](evaluation-record-template.csv)，默认12行A组NOT_RUN，仅供填报；无任何实测成绩。详细指标：

| 指标 | 计算或判定 |
| --- | --- |
| 任务完成率 | 完成全部必需步骤的用例数/实际测试用例数；遗漏和阻塞单列 |
| 事实一致性 | 逐条核对重要陈述与当时证据；查询正确与模型表述正确分开 |
| 定位正确性 | 正确绑定目标数/实际定位尝试数；另外检查五站覆盖与缺失拒绝 |
| 工单一致性 | 确认前新增、确认后新增、重试重复、编号/资产是否一致 |
| 耗时 | 记录准备、首个有效结果和完整完成；样本量及失败/超时单列，不只统计成功 |
| 费用 | 实际模型名/版本、请求数、供应商token/账单用量；没有返回用量时标未知，不填0 |

## 8. 六分钟视频的内容分配建议

| 时间段 | 展示 |
| --- | --- |
| 0:00—0:30 | 运维痛点、系统全景与数据来源 |
| 0:30—1:30 | S1五站巡检、异常/过期区别及设备定位 |
| 1:30—3:10 | S2多源取证、候选原因与知识依据，作为重点 |
| 3:10—4:20 | S3确认前后工单状态、真实编号及恢复复核 |
| 4:20—5:10 | 实测对照结果，展示样本量和失败情况 |

以上为团队录制安排，非官方分项时长。小智可作为S1提问入口，不单独占用长段功能介绍。剪辑不改变实际执行顺序和输出，等待过程如加速应标明；模拟注入、历史回放标签在片段中保留。正文、页面、桌面和语音中的身份信息按匿名要求检查，上传文件名按平台模板处理。

本轮完成的是规划和模板。未修改固件、Agent、数据库、运行模型及云端；未发送消息给其他对话。后续第一个实现单元为“31路台账映射与受限批量站点快照”，通过后接三维卡片和S1。

模型与硬件可按已确认布局继续，但每项按实际证据验收。官网约束与原件见[赛事核查](../competition-research-20261024/README.md)。本规划不改变已报名题目，不为竞争力新增未经验证的“预测准确率”或获奖承诺。
