# KK_UI 受控扩展

这是最后手段，不是制作普通页面的快捷入口。开始修改前完整阅读 [admission-and-review.md](references/admission-and-review.md)。

## 执行边界

1. 先用实际需求证明现有菜单、信息页、编辑器、覆盖层、无状态绘制辅助和全屏自定义页无法合理完成目标。
2. 判断需求是否跨页面或跨项目重复；单项目视觉、特殊图标、业务状态机和局部动画继续留在应用自定义页。
3. 在任何核心或公共 API 修改前，向用户给出最小设计、替代方案、Flash/RAM/状态/API 成本和裁剪策略，并获得明确同意。只有“实现页面”的授权不等于“扩展核心”的授权。
4. 获准后做最窄的可复用实现。保持单例、静态拓扑、无堆分配、无额外帧缓冲和 KK_UI 独占刷新。
5. 新模块必须有独立编译开关，未使用时可由链接器裁剪；不把成本或状态移到应用层来掩盖总资源。
6. 同步更新公共 API、设计说明、移植/使用 Skill 相关参考，以及目标工程已有的相关行为、视觉和裁剪验证。
7. 沿用目标工程自己的构建、测试、资源分析和运行方式复核扩展，并报告相对扩展前的资源差异；不要求固定编译器、构建配置、分析工具或硬件工具。

## 立即停止并改用其他路径

- 需求本身尚不明确：先返回需求讨论；不确定性不能作为扩展核心的证据。
- 增加菜单项、绑定、事件或普通页面：使用 `kk-ui-use`。
- 单个业务页面或运行时数据列表：使用自定义页和 `kk-ui-use`。
- MCU、刷新、输入硬件或屏幕尺寸迁移：使用 `kk-ui-port`。
- 新增文字或字形：使用 `kk-oled-font`。

不得借扩展任务引入通用控件树、运行时插件/回调注册、自动多分辨率布局、动态菜单增删或堆分配，除非用户明确改变产品定位并重新批准设计。
